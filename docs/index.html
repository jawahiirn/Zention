Islands Architecture in Next.js: How We Scaled Our Workspace Shell

How we refactored a monolithic client-side layout into a lean, server-first architecture using the Islands pattern in Next.js App Router.

JS
Engineering Team 8 min read · Next.js App Router · React Server Components

The Problem

As our workspace-based application grew, we noticed a pattern that would eventually become a bottleneck: our entire layout shell was a single Client Component.

Every button, every navigation link, every static piece of text in the sidebar — all of it was bundled into one massive JavaScript file that the browser had to download, parse, and hydrate before the app became interactive.

The workspace layout wraps every route in the application. It contains:

  • A resizable sidebar with drag-to-resize functionality
  • A workspace switcher dropdown
  • Navigation links with active state highlighting
  • A collapse/expand toggle button
  • Keyboard shortcuts (Cmd+B to toggle the sidebar)
  • A header bar with a sidebar trigger

As we planned to add more features — Spaces lists, notification badges, search, activity feeds — this single Client Component would only get larger. Every new feature would increase the JavaScript bundle that blocks the first interaction.

What is Islands Architecture?

The term "Islands Architecture" was coined by Jason Miller (creator of Preact). The core idea is elegantly simple:

Render the entire page as static HTML on the server. Then, "hydrate" only the small interactive parts — the "islands" — on the client.

Think of a webpage as an ocean of static content with small islands of interactivity scattered across it. The ocean is free (server-rendered HTML). The islands cost JavaScript.

🌊 Static HTML — server-rendered, zero JS cost
SidebarHotkeysClient Island — keyboard shortcuts
WorkspaceSwitcherClient Island — dropdown
SidebarNavLinkClient Island — active route
CollapseButtonClient Island — toggle
ResizableShellClient Island — resize logic only, receives server content via props

In Next.js App Router, this maps directly to:

  • Server Components = the ocean (zero client-side JS)
  • Client Components = the islands ('use client' directive)

Before: The Monolithic Client Shell

The entire sidebar — its structure, icons, link text, everything — shipped as JavaScript. React had to hydrate every element before anything was interactive.

The root WorkspaceShell was a Client Component, which forced AppSidebar to be one too. This cascading client boundary is the core problem.

workspace-shell.tsx — The Monolith
// ❌ The entire shell as one big Client Component
'use client';

export function WorkspaceShell({ children, sidebarVariant, initialLayout }) {
  const { state, setOpen, toggleSidebar } = useSidebar();
  const panelRef = useRef(null);

  // Layout persistence via cookies
  const onLayoutChanged = useCallback((layout) => {
    document.cookie = `sidebar:layout=${JSON.stringify(layout)}`;
  }, []);

  // Keyboard shortcut
  useHotkeys('mod+b', (e) => {
    e.preventDefault();
    toggleSidebar();
  });

  return (
    <ResizablePanelGroup>
      <ResizablePanel>
        {/* AppSidebar INSIDE Client Component = forced client */}
        <AppSidebar variant={sidebarVariant} />
      </ResizablePanel>
      <ResizableHandle />
      <ResizablePanel>
        {children}
      </ResizablePanel>
    </ResizablePanelGroup>
  );
}

Why This Was a Problem

Issue Impact
Everything is client JS All icons, link text, sidebar structure — shipped as JavaScript
Hydration cost React must hydrate every sidebar element before anything is interactive
Bundle bloat Adding any new sidebar section increases the JS bundle for every page
Cascading client boundary Because WorkspaceShell is 'use client', everything it imports is also forced client-side

After: The Islands Architecture

The refactored shell converts two large Client Components into Server Components, and extracts five tiny Client Islands — each with a single responsibility.

❌ Before
2 large Client Components
WorkspaceShell + AppSidebar

Everything ships as JS. Sidebar can't render until hydration completes.
✅ After
5 tiny Client Islands
Each does exactly one thing. The rest is server-rendered HTML, available on the first byte.

1. WorkspaceShell — Now a Server Component

The biggest change. The shell becomes an orchestrator — it decides what goes where, but delegates all interactivity to islands.

workspace-shell.tsx — Server Component
// ✅ No 'use client' — this is a Server Component
import { AppSidebar } from '@/shared/components/app-sidebar';
import { ResizableShell } from '@/shared/components/resizable-shell';
import { SidebarHotkeys } from '@/shared/components/sidebar-hotkeys';

export function WorkspaceShell({ children, workspaceId, sidebarVariant, sidebarOpen, initialLayout }) {
  return (
    <>
      <SidebarHotkeys />
      <ResizableShell
        sidebarVariant={sidebarVariant}
        initialLayout={initialLayout}
        sidebar={<AppSidebar variant={sidebarVariant} />}
        header={
          <header>
            <SidebarTrigger />
          </header>
        }
      >
        {children}
      </ResizableShell>
    </>
  );
}
sidebar and header are passed as props to ResizableShell. Because they are rendered by a Server Component and passed as serialized React Elements, they remain server-rendered even though ResizableShell is a Client Component.

2. ResizableShell — Client Island (the frame)

This island knows nothing about the sidebar's content. It only manages the resizing logic and accepts server-rendered content via props.

resizable-shell.tsx — Client Island
'use client';

export function ResizableShell({ children, sidebar, header, sidebarVariant, initialLayout }) {
  const { state, setOpen } = useSidebar();
  const panelRef = useRef(null);

  // … resizing logic, layout persistence, panel sync …

  return (
    <ResizablePanelGroup>
      <ResizablePanel>
        {sidebar} // ← server-rendered, just placed here
      </ResizablePanel>
      <ResizableHandle />
      <ResizablePanel>
        <SidebarInset>
          {header} // ← server-rendered, just placed here
          <div>{children}</div>
        </SidebarInset>
      </ResizablePanel>
    </ResizablePanelGroup>
  );
}

3. The Five Islands

Each island is a small, focused Client Component with a single responsibility:

SidebarNavLink — highlights the active route
'use client';

export function SidebarNavLink({ href, label, icon }) {
  const pathname = usePathname();
  const isActive = pathname === href;

  return (
    <SidebarMenuButton asChild isActive={isActive}>
      <Link href={href}>{icon}<span>{label}</span></Link>
    </SidebarMenuButton>
  );
}
SidebarHotkeys — registers keyboard shortcuts (renders nothing)
'use client';

export function SidebarHotkeys() {
  const { toggleSidebar } = useSidebar();
  useHotkeys('mod+b', (e) => { e.preventDefault(); toggleSidebar(); });
  return null;
}
SidebarCollapseButton — toggles the sidebar
'use client';

export function SidebarCollapseButton() {
  const { state, toggleSidebar } = useSidebar();
  const isCollapsed = state === 'collapsed';

  return (
    <SidebarMenuButton onClick={toggleSidebar}>
      {isCollapsed ? <ChevronsRight /> : <ChevronsLeft />}
    </SidebarMenuButton>
  );
}

Gotchas We Encountered

1. "Event handlers cannot be passed to Client Component props"

When we converted AppSidebar to a Server Component, any inline onClick broke the build. Server Components can't pass functions as props.

❌ Breaks
<Button onClick={() => {}}>
  <SquarePen />
</Button>
// onClick is a function —
// can't cross server→client
✅ Fix
<SidebarCreatePageButton />
// Extract into its own
// Client Island component

2. "Functions cannot be passed directly to Client Components"

We were passing Lucide icon components (which are functions) as props. The fix is to render the icon in the Server Component and pass the resulting element.

❌ Breaks — component is a function
<SidebarNavLink
  icon={item.icon}
/>
✅ Works — element is serializable data
<SidebarNavLink
  icon={<item.icon className="size-4" />}
/>

The distinction matters: a Component (Home) is a function — functions can't cross the server→client boundary. An Element (<Home />) is a plain object — objects can be serialized.

The Composition Pattern: Why Props, Not Imports

If a Client Component imports another component, that component is forced client-side.
If a Client Component receives another component via props, it retains its original type.

Think of it as the Architect vs. Contractor pattern. The Server Component (architect) decides what content goes where. The Client Component (contractor) only knows how to build an interactive frame — it doesn't care what you put inside it.

❌ Bad — importing forces AppSidebar to be client-side
'use client';
import { AppSidebar } from './app-sidebar'; // ← now it's client JS

export function ResizableShell({ children }) {
  return <ResizablePanelGroup><AppSidebar /></ResizablePanelGroup>;
}
✅ Good — receiving via props preserves server rendering
'use client';
// No import of AppSidebar!

export function ResizableShell({ children, sidebar }) {
  return (
    <ResizablePanelGroup>
      {sidebar} // ← remains server-rendered
    </ResizablePanelGroup>
  );
}

The most meaningful win: sidebar HTML is now rendered in the first byte. Navigation links and structure are visible before any JavaScript loads — which means faster First Contentful Paint and a better experience on slow connections.

Adding new static sidebar sections now has zero JavaScript cost. Only interactive islands add to the bundle.

When to Use This Pattern

✓ Use it when
  • Your layout wraps many routes and will grow over time
  • Most of the layout is structural with pockets of interactivity
  • You care about First Contentful Paint and Time to Interactive
  • You want to add features without growing your JS bundle
✗ Skip it when
  • The entire component is inherently interactive (drawing canvas, real-time chat)
  • The component is small and unlikely to grow
  • You're building a prototype where iteration speed matters more

What's Next

With the Islands Architecture in place, the workspace shell is ready for advanced optimizations:

  1. Suspense Streaming — Wrap future data-fetching sidebar sections (like "Spaces List") in <Suspense> boundaries so the shell loads instantly while data streams in.
  2. Partial Prerendering (PPR) — Pre-render the static shell as cached HTML on a CDN. Dynamic islands stream in on request.
  3. Dynamic Imports — Use next/dynamic with ssr: false for heavy features like command palettes that aren't needed on first paint.

The beauty of this architecture is that each optimization can be applied incrementally — one island at a time, one section at a time — without rewriting the entire shell.

Built with Next.js App Router, React Server Components, and a healthy respect for the client-side JavaScript budget.
